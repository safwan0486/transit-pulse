The journey of one bus ping

The project handles every bus and train in the feeds: about 200–250 vehicles every 30 seconds, roughly 500 positions a minute. To make the path easy to follow, this section traces one example record, a GPS reading from bus WVC3917 on route U8220. Every other vehicle's reading takes exactly the same path at the same time.

data.gov.myPublishes all bus positions as a protobuf file, updated every ~30 s
→
ProducerDownloads it, turns each bus into a JSON record, sends to Kafka
→
KafkaStores the record in order, lets many readers consume it
→
SparkValidates, fixes units, removes duplicates → silver (or quarantine)
→
dbt + DuckDBMatches pings to scheduled stops, computes delay and bus spacing
→
DashboardShows punctuality, bunching and a live map

Two things run beside this main line: Airflow downloads the official timetables every morning (needed to know where a bus should be), and the Phase 4 jobs watch the whole line and alert you when anything stops.

The medallion lake: bronze → silver → gold

Bronze = raw data exactly as received, never changed (your insurance: you can always rebuild from it). Silver = cleaned, typed, deduplicated. Gold = business-ready summary tables for the dashboard. Each layer only reads from the one before it. This pattern is used at almost every company with a data lake, so interviewers expect you to know it.

Phase 1

Ingestion: getting data in

Goal: reliably collect live GPS every 30 seconds and the timetables every day, without losing data when something restarts.

How it flows

  1. producer.py wakes up every 30 s and calls the data.gov.my API for each feed (Rapid KL, MRT feeder, KTMB).
  2. The answer is a protobuf file (a compact binary format, not JSON). gtfs_rt.py decodes it into one Python dict per vehicle.
  3. Each record gets an event_id = feed:vehicle:timestamp. The same bus at the same moment always gets the same id, which makes duplicates detectable later.
  4. The producer skips records it already sent (the API repeats a bus until it reports again), then sends the rest to the Kafka topic gtfs.vehicle_positions.
  5. bronze_sink.py reads from Kafka, collects records for up to 5 minutes, writes them as one Parquet file to bronze/, and only then tells Kafka "done" (commits the offset).
  6. Separately, every day at 03:00 Malaysia time, the Airflow DAG gtfs_static_ingest downloads each feed's timetable zip, saves it to bronze, checks that the required files exist, and converts every table to Parquet in silver.

Key idea: at-least-once + a natural key = safe

Perfect "exactly once" delivery is hard and expensive. Instead, the pipeline accepts that a record might arrive twice (never zero times), and gives every record a natural key (event_id) so later stages can remove the duplicate. This is the standard real-world approach.

Why these tools

Kafka (Redpanda locally)

vs RabbitMQ, Pub/Sub, Kinesis
Why
Kafka keeps messages after they are read, so you can replay (we rebuilt silver from it). Many readers can consume the same data independently. It's the industry standard for streaming and appears in most DE job ads.
Why Redpanda
It speaks the exact Kafka protocol but is one small program with no Java and no ZooKeeper. Your Docker only had ~3.9 GB RAM; Apache Kafka would use much more.
Pick the alternative when
RabbitMQ: task queues where each message is processed once and deleted. Pub/Sub or Kinesis: on Google Cloud or AWS, when you want it fully managed.

Parquet

vs CSV, JSON
Why
Columnar: a query reading 3 columns skips the other 18. Compressed (often 5–10× smaller than CSV) and stores types (a number stays a number).
Pick the alternative when
CSV/JSON only for tiny files people open by hand, or for systems that can't read Parquet.

S3 API (SeaweedFS locally)

vs local folders, MinIO
Why
Code written against the S3 API runs unchanged on AWS S3 or Google Cloud Storage. A local folder would need rewriting for the cloud.
Why not MinIO
MinIO was the plan (it's the usual choice) but its free Docker images were no longer downloadable. SeaweedFS is an open-source replacement.

confluent-kafka

vs kafka-python
Why
Built on the fast C library librdkafka, actively maintained, supports idempotent producing. kafka-python is pure Python, slower, and maintained less actively.

Airflow for the daily job

vs cron
Why
Cron only starts a script. Airflow adds retries, a UI with logs, alerts, backfills of past days, and dependencies between steps.
Pick the alternative when
One simple script on one server, where a failure is harmless.

Phase 2

Stream processing: cleaning in real time

Goal: turn raw Kafka records into trustworthy silver data within about a minute, separate the bad records, and remove duplicates, all without losing or double-counting data if Spark restarts.

How it flows

  1. Every 60 s, Spark reads all new Kafka messages (a micro-batch).
  2. parse_kafka turns the JSON text into typed columns. Broken JSON becomes empty values but the raw text is kept.
  3. standardize converts timestamps, fixes the speed unit (km/h, proven with GPS math), sets KTMB's fake speed to empty, and adds the Malaysian date.
  4. add_quality_flags gives each record a dq_reason: empty if good, otherwise the first rule it broke (missing GPS, outside Malaysia, faster than 160 km/h, timestamp in the future…).
  5. Good records go through dedupe (same event_id within 15 minutes = duplicate) and are written to silver. Bad records go to quarantine with their reason.
  6. Spark saves its position in Kafka and its "seen ids" memory in a checkpoint, so after a restart it continues exactly where it stopped.

Key idea: the watermark limits memory

To catch duplicates, Spark must remember every id it has seen. A stream never ends, so memory would grow forever. The 15-minute watermark says: "only remember ids from the last 15 minutes of event time; data later than that is dropped." For 30-second bus positions, losing very late data is acceptable. For payments it would not be.

Why these tools

Spark Structured Streaming

vs Flink, Kafka Streams, plain Python
Why
Gives you checkpoints, watermarks, stateful dedupe and exactly-once file output built in. Spark is the most requested processing engine in DE job ads, and the same API works for batch.
Pick the alternative when
Flink: true per-event processing with millisecond latency and complex state (fraud detection). Kafka Streams: Java/Scala apps that read and write Kafka only. Plain Python (like our bronze sink): simple copying with no state.

PySpark (Python)

vs Scala Spark
Why
The DataFrame code becomes the same optimized plan on the Java engine, so there's no speed loss as long as you avoid Python UDFs (we have none). Python is what most DE teams write.

Quarantine instead of dropping

vs filtering bad rows away
Why
Dropped rows are invisible: you never learn that a feed broke. Quarantined rows can be counted, alerted on (Phase 4 does) and replayed after a fix. That's how we found null island and the 2029 clock.

RocksDB state store

vs default in-memory store
Why
Keeps dedupe memory on disk instead of in Java memory, so a big state doesn't crash a small machine.

Phase 3

Warehouse: turning data into answers

Goal: answer "is this bus late?" The feeds only give GPS positions, so the warehouse has to work out when a bus reached each stop, then compare that with the timetable.

How it flows (dbt layers)

stagingRename, cast types, one model per source. Views.
→
intermediateReusable joins: trips + stops + timetable snapshot.
→
coreFacts and dimensions (star schema). Tables.
→
performance / monitoringDaily and hourly answers for people.
  1. Staging reads silver Parquet in place from the lake (DuckDB's read_parquet over S3; nothing is copied).
  2. fct_stop_arrivals matches each GPS ping to its trip's scheduled stops within 150 m. Because 94% of MRT feeder trips are loops, each ping is assigned to one stop visit only: the one closest to its scheduled time.
  3. MRT feeder has exact times per stop, so delay = observed − scheduled → mart_route_on_time_daily and mart_network_delay_hourly.
  4. Rapid KL runs "every N minutes", so we measure gaps between actual departures → mart_dispatch_headways → mart_route_headway_daily.
  5. dbt build runs every model and its tests in order. If a test fails, everything after it is skipped, so bad data never reaches the dashboard.

Key idea: star schema

Facts are events with numbers (each stop arrival, each GPS ping). Dimensions describe them (which route, which stop). Marts join facts to dimensions and aggregate. Interviewers often ask you to explain this, and SCD Type 2 ("how do you keep history when a dimension changes?").

Why these tools

dbt

vs plain SQL scripts, stored procedures, SQLMesh
Why
Models depend on each other through ref(), so dbt runs them in the right order and draws the lineage. Tests, documentation and incremental loading come built in. It's the standard tool for analytics engineering.
Pick the alternative when
Plain SQL for one or two queries. SQLMesh is a newer rival with built-in column-level lineage and virtual environments; fewer jobs ask for it.

DuckDB

vs PostgreSQL, BigQuery, Snowflake
Why
Free, no server, very fast for analytics, and reads Parquet straight from the lake. Perfect for a laptop.
Its limit
Only one program can write to the file at a time. That's why Phase 5 added the gold layer.
Pick the alternative when
BigQuery/Snowflake: a team, big data, many users at once (Terraform in Phase 4 prepares BigQuery). PostgreSQL: an app database with many small writes; slower for analytics.

Daily snapshots → SCD2

vs dbt snapshots
Why
dbt snapshots only record changes while dbt runs; miss a day and history has a hole. Building SCD2 from the daily timetable files in the lake can be rebuilt at any time and always gives the same result.

Two metrics for two timetable styles

vs one "delay" for everything
Why
Rapid KL publishes no fixed times, so "delay" doesn't exist for it. Using the metric that fits each service (on-time % vs headway adherence) is how transit agencies such as Transport for London measure it.

Phase 4

Hardening: running safely without you watching

Goal: notice problems before users do, keep the lake tidy, and make the cloud setup repeatable.

How it flows

  1. Every 15 min, pipeline_health checks each stage: newest bronze file, newest silver file, Kafka lag of the sink, quarantine rate, and timetable age.
  2. If a check fails, it sends one alert to Discord/Slack, and one more when everything recovers. It remembers the last state in an Airflow Variable so it doesn't repeat itself.
  3. Every DAG also alerts when a task fails after its last retry (on_failure_callback).
  4. Every hour, bronze_compaction merges the small bronze files of each finished hour into one file.
  5. dbt's mart_feed_health_hourly and two warning tests catch frozen feeds and trips that stop matching the timetable.
  6. Terraform describes the Google Cloud resources as code, checked in CI.

Key idea: idempotent = safe to run twice

An idempotent job gives the same result whether it runs once or five times. Every job in this project is built that way (date-based output paths, hash-named files, delete-after-verify), so retries and backfills never create duplicates. Say this word in interviews.

Dashboard: showing the answers

Goal: one page that tells a non-engineer how reliable buses are today, with a live map, without slowing down or breaking the warehouse.

How it flows

  1. At the end of every dbt build, the export_gold macro copies 4 summary tables to gold/*.parquet in the lake.

Things we wanted but couldn't use

!

MinIO (the usual local S3) → its free Docker images were no longer downloadable (Docker Hub said "access denied", quay.io "unauthorized"). We used SeaweedFS instead.

!

BigQuery → needs your own Google Cloud account and billing, which only you can create. We used DuckDB now; the Terraform for BigQuery is written and validated, ready when you are.

!

Airflow 3 → released 2025 with big changes (new API server, CLI and UI changes). We chose the stable, well-documented 2.10.5. Upgrading is a good future exercise.

!

dbt inside Airflow's Python → their package versions conflict. We installed dbt in a separate virtual environment in the same image (a common real-world fix; the Cosmos library is another option).

!

Apache Kafka itself → too much memory for the ~3.9 GB Docker had. Redpanda is Kafka-compatible and much lighter.

!

Running Spark tests on Windows → your Java 21 isn't officially supported by Spark 3.5, so tests run inside the Spark container instead (works the same in CI).

!

Delta Lake / Iceberg → would have been better (see the table above) but add complexity. Plain Parquet kept the focus on the pipeline. A strong "what would you improve?" answer.

Phase 1 · Why does the bronze sink commit Kafka offsets after writing the file, not before?

If it committed first and then crashed before writing, those messages would be lost forever. Committing after means a crash can only cause the batch to be written again (a duplicate), which later stages remove using event_id. This is "at-least-once" delivery.

Phase 1 · Why are Kafka messages keyed by vehicle?

Messages with the same key always go to the same partition, and order is guaranteed inside a partition. So each bus's positions stay in time order, even with many partitions and parallel readers.

Phase 1 · Why is bronze partitioned by ingestion time but silver by event date?

Bronze is append-only raw data: grouping by when it arrived makes it easy to reprocess "everything from 2–3 PM". Silver is for analysis, and people ask about when things happened, in Malaysian time, so silver uses the event's local date.

Phase 2 · What does a Spark checkpoint store, and why does it matter?

The Kafka positions already processed, and the dedupe state (ids seen recently). After a restart, Spark continues from exactly there: no data skipped, nothing counted twice.

Phase 2 · Why put the cleaning logic in transforms.py separately from the job file?

The functions take a DataFrame and return a DataFrame, with no Kafka or S3. That makes them testable with small fake data in seconds, and the same logic works for streaming and for batch backfills.

Phase 3 · How do you know when a bus reached a stop, if the feed never says so?

Match each GPS ping to its trip's scheduled stops within 150 m. Because most MRT feeder routes are loops, each ping is assigned to only one stop visit (the one nearest its scheduled time), and for each stop visit we keep the closest ping. Matches more than 30 minutes off schedule count as mismatches, not delays.

Phase 3 · What is SCD Type 2 and where is it used?

A way to keep history in a dimension: when a route changes, the old row gets a valid_to date and a new row starts with valid_from. Facts join to the version that was valid on their date. Used in dim_route, built from the daily timetable snapshots.

Phase 3 · What does "incremental" mean in fct_stop_arrivals?

Instead of rebuilding the whole table every hour, dbt only processes the last day and replaces those rows (delete + insert by key). The one-day lookback makes sure trips that cross the cut-off are rebuilt completely.

Phase 3 · Why two different metrics for Rapid KL and MRT feeder?

MRT feeder publishes an exact time for each stop, so delay can be measured. Rapid KL only says "every N minutes", so there is no scheduled time to be late against; instead we check whether departures are evenly spaced, bunched or have gaps.

Phase 4 · Why alert only on state changes?

To avoid alert fatigue. A 3-hour outage would otherwise send 12 identical alerts and people start ignoring them. One "failing" alert and one "recovered" alert are enough.

Phase 4 · How is compaction made safe to re-run?

The output file name is a hash of the input file names; inputs are deleted only after the output's row count is checked; and rows are deduplicated by Kafka partition + offset. If it crashes midway, the next run finishes the job without creating duplicates.

Phase 5 · Why doesn't the dashboard read the DuckDB warehouse directly?

DuckDB allows only one writer at a time. While dbt runs, the dashboard would get "file locked" errors. Exporting tested tables to gold Parquet separates serving from building, and any engine can read Parquet.

Phase 5 · Tell the story of the wrong wait-time metric in under a minute.

The dashboard showed +27 min, which seemed too high. Only 34% of stop passes were caught because GPS comes about once a minute, so gaps looked twice as long. I switched to gaps between actual departures (ratio 2.04 → 1.23), dropped gaps from before data collection started (1.06), and made "% evenly spaced" the headline because wait time is skewed by a few long gaps. Lesson: investigate surprising numbers before publishing.

Overall · What would you improve with more time and a cloud budget?

Move to managed cloud services using the Terraform (GCS, BigQuery, managed Kafka); switch the lake to Iceberg or Delta for transactions and compaction; replace the health DAG with Prometheus + Grafana; publish dbt docs; and collect weeks of data so trends are meaningful.
